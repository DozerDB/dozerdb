# DozerDB 5.26.32-1.2.0

Long-term-support release of DozerDB 1.2.0 on Neo4j `5.26.32`: it adds
Neo4j-compatible query logging and `dbms.setConfigValue`.

## Versioning

Release names changed with this release. A release is now named
`<neo4j-tag>-<dozerdb-version>`: the first half is the exact Neo4j tag it is
built on, the second half is DozerDB's own `MAJOR.MINOR.PATCH` version, which
moves only when what DozerDB adds to Neo4j changes (MAJOR for a breaking change,
MINOR for an addition, PATCH for a fix). A Neo4j upgrade alone changes only the
first half. `1.2.0` is the first independent DozerDB version: it is a MINOR
release because it adds query logging and `dbms.setConfigValue` to the `1.1.0`
components that `5.26.32.1` shipped. Under the earlier rule, the Neo4j tag
plus a DozerDB revision counter, this release would have taken the next counter
after `5.26.32.1`; it is published only under the new name. Earlier releases
keep their names: `5.26.32.0`, `5.26.32.1` and their tags, files and Docker
images stay valid and unchanged.

plugin JAR, the archives and the Docker image alike.

## What is in this release

- Query logging as the Neo4j Operations Manual 5 documents it: every
  `db.logs.query.*` setting with Neo4j's name and default, `query.log` in the
  logs directory with Neo4j's plain-text line or, through `server-logs.xml`,
  Neo4j's JSON fields, entries for queries and for transactions, and changes at
  runtime through `dbms.setConfigValue`. The
  [query logging](../monitoring/query-logging.md) page says what applies; the
  [query log compatibility](../monitoring/query-log-compatibility.md) page lists
  every setting and field with its tier and the shapes DozerDB defines where
  Neo4j's documentation is silent.
- `dbms.setConfigValue`, Neo4j's procedure for changing a dynamic setting without
  a restart, with Neo4j's signature, mode and description
  ([procedures](../procedures.md)).
- The plugin JAR, the standalone archives and the Docker image carry the same
  query log and the same procedure; the Docker image writes `query.log` to
  `/logs`, and the `NEO4J_db_logs_query_*` variables set the settings.
- `neo4j-admin server report` collects `query.log` with the other logs.

## Compatibility notes

- Query logging is on by default, as in Neo4j Enterprise: with no
  `db.logs.query.*` setting, DozerDB writes a start and an end entry for every
  query to `logs/query.log` at the `VERBOSE` detail level, rotating at 20 MB and
  keeping 7 files. Set `db.logs.query.enabled=INFO` to keep only the end
  entries of queries slower than `db.logs.query.threshold`, or `OFF` to write
  none; both apply without a restart. Transaction entries stay off unless
  `db.logs.query.transaction.enabled` is set. Query text and parameters appear
  in the log; where it must not carry data values, set
  `db.logs.query.obfuscate_literals=true` or
  `db.logs.query.parameter_logging_enabled=false`.
- Under a heavy load of short queries the query log costs throughput, because
  Neo4j's shipped logging configuration flushes the file after every entry:
  measured under sixteen clients issuing sub-millisecond queries in a closed
  loop, the default configuration served 95 % fewer requests per second than
  with the log off. An ordinary workload pays a fraction of that. The
  [query logging](../monitoring/query-logging.md#cost-under-load) page gives
  the two-line `server-logs.xml` edit that brought the measured cost under 1 %,
  and its durability trade-off.
- The query log follows Neo4j 5.26: `db.logs.query.annotation_data_format`
  defaults to `CYPHER`, a JSON entry has no `queryLang` key, and
  `db.logs.query.obfuscate_errors` writes the standard description of the
  error's GQLSTATUS code, since Neo4j 5.26 has no obfuscated one. An error
  Neo4j 5.26 raises without a GQL status of its own, such as a variable not
  defined, carries the default `50N42` in `errorInfo`, with no position.
- Where the manual documents no shape (the start entry, a failed query, the
  transaction entries, the plan table), DozerDB's own shape is recorded as
  Partial on the compatibility page with an example line, and a parser written
  for Neo4j Enterprise's output may need to accept it.
- DozerDB 5.26.32-1.2.0 is built on the same Neo4j `5.26.32` as 5.26.32.1; data
  directories from earlier DozerDB 5.26 releases open unchanged.
- The Windows archive is verified by inspection of its contents and launchers;
  it is not run as part of the release checks.
- Neo4j's Cypher `WAIT` clause on database management commands is not
  supported.

## Verification

The release archives, the plugin JAR and the Docker image passed the packaged
smoke tests, the metrics checks, the query log check (nine probes against
`query.log` on every delivery form, including the JSON layout on the
distribution), the Cypher constraint and database lifecycle flow and the Browser
flow described in [building.md](../building.md). Checksums are published beside
each file on the GitHub release.
